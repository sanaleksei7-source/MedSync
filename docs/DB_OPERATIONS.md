# База данных: устройство, шифрование, копии, восстановление

Шаг 3.2 плана разработки. Всё проверено на вымышленных данных. **Выбор места, где будет работать база в рабочем режиме, зависит от юридического ответа о хранении данных** (`docs/LEGAL_QUESTIONS_RU.md`); код от этого выбора не зависит.

## 1. Что используется

| Среда | Движок | Как включается |
|---|---|---|
| Разработка, тесты, небольшой стенд | **PGlite**: настоящий PostgreSQL внутри Node, данные в папке `data/db` | по умолчанию |
| Рабочая среда | Обычный сервер **PostgreSQL** | переменная `DATABASE_URL` |

Код один и тот же: слой `server/db/db.ts` скрывает разницу. Что **проверено**: все тесты проходят на PGlite (PostgreSQL 17 в WebAssembly). Что **не проверено**: подключение драйвера `pg` к настоящему серверу PostgreSQL, потому что сервера в этой среде нет. Перед рабочим использованием это нужно прогнать на реальном сервере (`npm test` с `DATABASE_URL` и проверка по разделу 6).

## 2. Что хранится

Одна таблица `visits` (схема: `server/db/migrations/0001_visits.sql`):

- Открытые служебные поля: идентификатор приёма, идентификатор врача и пациента, тип документа, статус, версия, даты, хэш подписи. Имён, ПИН и медицинского текста тут **нет**.
- Одно зашифрованное поле `payload`: расшифровка разговора, черновик, решения врача, журнал изменений, подпись.

Защита в самой базе (проверена тестами):

- Подписанный приём **нельзя изменить или удалить даже прямым запросом к базе** (триггер). Ошибка в программе не сможет переписать подписанный документ.
- Ограничения: статус «подписан» возможен только с хэшем, идентификатор приёма имеет строгий формат.
- Оптимистичная блокировка по версии: два одновременных изменения не затирают друг друга, проигравший получает отказ.

## 3. Шифрование

Три слоя, каждый закрывает своё:

1. **Шифрование полей в программе (сделано).** AES-256-GCM, свежий случайный `nonce` на каждую запись. К шифртексту привязаны идентификаторы приёма, врача и пациента (AAD): строку нельзя подставить под другой приём, передать другому врачу или другому пациенту. Любая правка шифртекста или привязки обнаруживается при чтении. Копия базы или файл резервной копии без ключа не раскрывают текст.
2. **Шифрование диска и самой базы (делает хостинг, не сделано здесь).** BitLocker / LUKS / шифрование тома у облачного провайдера; для сервера PostgreSQL в рабочей среде. Нужно выбрать вместе с хостингом (шаг 3.7).
3. **Шифрование канала к базе.** Для `DATABASE_URL` указывайте `sslmode=verify-full`.

### Ключи

- Ключ задаётся переменной `DATA_KEYS` в `.env` (файл не попадает в Git). Создать: `npm run db:setup`. Ключ не печатается.
- Формат: `id:base64,id:base64`. **Первый ключ** шифрует новые записи, остальные нужны, чтобы читать старые.
- **Потеря ключа = потеря данных.** Хранить копию ключа отдельно от копий базы (менеджер паролей, сейф). Ключ и копия базы в одном месте убирают смысл шифрования.
- В рабочей среде ключ должен лежать в менеджере секретов хостинга, а не в файле.
- **Смена ключа.** Добавьте новый ключ **первым**: `DATA_KEYS=k2:…,k1:…`. Новые записи пойдут с `k2`, старые читаются по `k1`. **Старые ключи нельзя убирать, пока есть записи, зашифрованные ими.** Перешифровки старых записей пока нет: подписанные приёмы нельзя менять даже в базе, и для них нужен отдельный проверенный порядок. Это известное ограничение.

## 4. Миграции

Файлы `server/db/migrations/NNNN_имя.sql` применяются по порядку при запуске сервера и командой `npm run db:status`. Каждая миграция идёт в своей транзакции и записывается с контрольной суммой: **уже применённую миграцию править нельзя**, нужна новая (проверено тестом).

## 5. Резервные копии

```powershell
npm run db:backup -- C:\путь\copy-2026-11-27.json
```

- Копия содержит открытые служебные поля и **зашифрованный** текст, плюс список применённых миграций и контрольную сумму файла. Ключ в копию не входит.
- Существующий файл не перезаписывается. Повреждённый или изменённый файл не принимается при восстановлении.
- Копия сохраняет и защиту: восстановленный подписанный приём тоже неизменяем.

### Что нужно настроить на хостинге (не сделано здесь)

- Расписание копий, например каждый час (журнал изменений) и раз в сутки (полная), срок хранения, и копия в **другом месте** (не на том же диске и не в той же учётной записи).
- Цели, которые должен утвердить владелец продукта с клиникой: **RPO** (сколько данных допустимо потерять) и **RTO** (за сколько вернуть работу). Сейчас они не заданы.
- Для сервера PostgreSQL дополнительно использовать его штатные средства (непрерывное архивирование WAL), а `db:backup` оставить как переносимую копию и средство проверки.

## 6. Проверка восстановления (restore drill)

Копия, которую ни разу не восстанавливали, копией не считается.

```powershell
npm run db:drill
```

Команда берёт копию текущей базы, разворачивает её во **временную пустую базу в памяти** и проверяет: каждая строка расшифровывается и проходит проверку подлинности, а у каждого подписанного приёма **хэш документа пересчитывается заново и сверяется с подписанным**. Рабочую базу не меняет. Код выхода: 0 — копия пригодна, 1 — есть проблемы.

Само восстановление:

```powershell
npm run db:restore -- C:\путь\copy-2026-11-27.json
```

Только в **пустую** базу, одной транзакцией: при ошибке не остаётся ничего. Копия от другой версии схемы отклоняется.

Проверка целостности рабочей базы в любой момент: `npm run db:status`.

### Результат проверки (2026-11-27, вымышленные данные)

База из 5 приёмов (1 подписанный): копия 21 КБ, восстановлено 5, проблем целостности 0, около 3 секунд. Файл копии не содержит читаемого текста. Восстановление в непустую базу отклонено. С неверным ключом проверка целостности сообщает о проблемах по всем строкам. Тесты (`server/db/db.test.ts`, 51 проверка) дополнительно показывают, что обнаруживаются: подмена шифртекста, перенос шифртекста между приёмами, смена врача или пациента напрямую в базе, повреждённый файл копии, откат восстановления, расхождение текста подписанного документа с его хэшем.

**Это проверка на малой вымышленной базе, на одном компьютере.** На рабочем объёме и на настоящем сервере PostgreSQL проверку нужно повторить и записать время восстановления.

## 6а. Журнал аудита (шаг 3.4)

- Лежит в таблице `audit_log` (миграция 0002). База сама **отказывает** в изменении, удалении и очистке записей, во вставке с пропуском номера или с неверной ссылкой на предыдущую запись (проверено тестами, `server/db/db.test.ts`). Прежний файл `data/audit.log` при первом запуске переносится в таблицу с проверкой цепочки; сам файл остаётся.
- Входит в резервную копию и в проверку восстановления (`db:drill`, `db:status` проверяют цепочку).
- **Сбой записи журнала останавливает сервер** (ответ 503 на все запросы): действие без следа в журнале недопустимо.
- Срок хранения: `AUDIT_RETENTION_YEARS` (предварительно 5, определит юрист). `npm run audit:status` показывает размер, самую раннюю запись и сколько записей старше срока. Автоматически ничего не удаляется.
- **Якорь:** `npm run audit:anchor -- C:\путьnchor-2026-11-27.json` сохраняет номер и хэш последней записи; файл нужно положить во внешнее хранилище, где его нельзя изменить. `npm run audit:check -- <файл>` проверяет, что журнал не урезан и не переписан целиком. Проверено на трёх случаях: совпадение, урезанный журнал, журнал, пересобранный с нуля.
- **Что не сделано:** автоматическая отправка якорей и журнала во внешнее хранилище и проверка подделки против настоящего хранилища (зависит от выбора хостинга, шаг 3.7); оповещения пока только в журнале, на экране аудитора и в консоли сервера.
- Правила тревог (`server/alerts.ts`): 5 отказов в доступе за 10 минут; 10 неудачных входов под одним именем; повторное использование токена; 100 чтений карт за 10 минут; работа с данными пациентов с 22:00 до 06:00 по Бишкеку. Пороги стартовые, нужно подобрать на реальной нагрузке. Состояние счётчиков хранится в памяти и после перезапуска начинается заново.

## 8. Учётные записи (шаг 3.5)

- Пользователи лежат в таблице `users`. Секрет второго фактора (и новый секрет, ожидающий подтверждения) шифруются тем же ключом `DATA_KEYS`, привязаны к идентификатору пользователя; хэш пароля — scrypt. Прежний файл `data/users.json` при первом запуске сервера один раз переносится в таблицу (файл остаётся; после проверки его лучше удалить, в нём хэши и секреты).
- **Потеря ключа `DATA_KEYS` теперь означает ещё и потерю секретов второго фактора:** все пользователи не смогут войти, их нужно будет создавать заново.
- Резервная копия (`db:backup`) пока **не содержит** таблицу пользователей; она содержит приёмы и журнал аудита. Пользователей нужно добавить в копию до рабочего запуска.
- Первый администратор создаётся `npm run seed` (вымышленные данные). Дальше пользователей создаёт администратор в приложении; одноразовые пароль и секрет показываются ему один раз.
- Забытый пароль или потерянный телефон: администратор нажимает «Сбросить пароль» (или «Сбросить пароль и второй фактор»); все входы пользователя завершаются, при следующем входе он обязан задать свой пароль и заново подключить второй фактор. Если потеряны и пароль, и доступ единственного администратора, восстановление возможно только через базу; процедуру нужно описать до рабочего запуска.
- Экстренный доступ (break-glass): врач вводит ПИН пациента и выбирает причину из списка; 30 минут, не больше трёх карт, чтение и ведение приёма без подписи. Выдача хранится в памяти сервера, при перезапуске все экстренные доступы закрываются. Каждый случай записан в журнал и вызывает тревогу `breakglass` у аудитора; введённый ПИН и свободный текст в журнал не пишутся.
