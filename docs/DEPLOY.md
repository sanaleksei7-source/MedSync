# Публикация MedSync в интернете

Шаг 3.7 плана разработки. **Хостинг ещё не выбран:** где будет сервер, зависит от юридического ответа о месте хранения данных (`docs/LEGAL_QUESTIONS_RU.md`, вопросы о размещении и вопрос 30 о передаче по открытым сетям). Всё ниже подготовлено и проверено тестами в среде разработки; **на настоящем сервере не запускалось.** До юридического разрешения — только вымышленные данные.

## 1. Схема

```
телефон / браузер ──https──▶ Caddy :443 ──▶ статические файлы (dist)
                                     └──▶ /api ──▶ Node MedSync 127.0.0.1:8787 ──▶ PostgreSQL (127.0.0.1)
                                                                          └──▶ распознавание речи (внутренний адрес, https)
```

- Снаружи открыты только порты 80 и 443 (Caddy) и SSH с адреса администратора (`deploy/firewall.sh`).
- Node слушает только `127.0.0.1:8787`; порт наружу не открыт.
- Сервис распознавания речи не публикуется вообще: сервер MedSync отказывается работать с ним по открытому http или по внешнему адресу (`server/asr/engine.ts`).

### Тревоги о входе

В журнал аудита к каждому входу пишется **метка адреса** (HMAC от адреса с ключом сервера), а не сам адрес. Новые правила (`server/alerts.ts`):

- **Перебор учётных записей** с одного адреса: 20 неудачных входов под 3+ именами за 10 минут.
- **Вход после неудач:** успешный вход после 3+ неудачных попыток под тем же именем.
- **Вход с нового адреса** для этого пользователя (после перезапуска сервера известные адреса восстанавливаются из журнала).
- Остаются прежние: подбор пароля под одним именем, повтор токена обновления, массовое чтение, ночная работа, экстренный доступ.

«Невозможное перемещение» (вход из двух далёких стран за короткое время) не сделано: нужна база географии адресов; решим вместе с хостингом.

Тревоги доставляются людям, если задано хотя бы одно:

- `ALERT_WEBHOOK_URL` — любой вебхук, принимающий `{"text": "..."}` (Slack, Mattermost и т. п.), только https;
- `ALERT_TELEGRAM_BOT_TOKEN` и `ALERT_TELEGRAM_CHAT_ID` — сообщения в чат Telegram.

В сообщении только правило и идентификаторы (номер пользователя, метка адреса, номер пациента при экстренном доступе) — без ФИО, ПИН и медицинского текста. Сбой доставки не останавливает сервер: тревога в любом случае уже записана в журнал. **Учтите:** Telegram — внешний сервис за рубежом; даже идентификаторы туда отправлять можно только после согласования с юристом.

## 3. Установка (Ubuntu 24.04, примерный порядок)

1. Пользователь и папки: `adduser --system --group medsync`; код в `/srv/medsync`, данные в `/srv/medsync/data` (владелец `medsync`, права 700).
2. Node 24, `npm ci`, `npm run build` (папка `dist`).
3. PostgreSQL на этом же сервере или отдельном (только внутренняя сеть, `sslmode=verify-full`). Шифрование диска — средствами хостинга.
4. `/etc/medsync/env` по образцу `deploy/env.example` (права 600). Ключ `DATA_KEYS` — отдельно сохранить в сейф/менеджер паролей.
5. `deploy/medsync.service` → `/etc/systemd/system/`, `systemctl enable --now medsync`.
6. Caddy 2.8+ из официального репозитория; `deploy/Caddyfile` → `/etc/caddy/Caddyfile`; переменная `MEDSYNC_DOMAIN`. **Сначала** `caddy validate --config /etc/caddy/Caddyfile`, потом `systemctl reload caddy`.
7. `sudo ADMIN_IP=… sh deploy/firewall.sh`.
8. Проверка: раздел 5.

## 4. Отказ в обслуживании (DoS) и работа без сервера

Клиника без связи с сервером не может работать в MedSync. План:

- **Защита у провайдера:** выбрать хостинг с защитой от DDoS на уровне сети или поставить перед сервером сервис фильтрации; это условие при выборе хостинга (вместе с юристом: фильтрующий сервис видит трафик).
- **Защита в программе (второй рубеж):** ограничения по адресу клиента (600 в минуту — с запасом на клинику за одним адресом), по имени при входе, по пользователю для распознавания и составления документа; предел размера запроса в прокси (2 МБ) и в сервере; короткие таймауты заголовков.
- **Работа без сервера:** врач оформляет документ вручную, как до MedSync. Приложение ничего не хранит на телефоне и при отсутствии связи показывает страницу «нет связи». Порядок «что делать, если MedSync недоступен» нужно согласовать с клиникой до пилота.
- **Наблюдение:** внешняя проверка доступности (раз в минуту) с оповещением; журнал прокси; тревоги MedSync.
- **Восстановление:** см. `docs/DB_OPERATIONS.md` — копии, проверка восстановления, время восстановления (RTO) ещё не утверждено.

## 5. Проверка опубликованного сайта

```powershell
npm run check:site -- https://medsync.example.kg 8080
```

Скрипт проверяет: доверенный сертификат и срок, TLS 1.2/1.3, отказ TLS 1.0/1.1, переход с http на https, заголовки страницы и API, ответ API без входа (401), что порты 8787 и порт распознавания закрыты снаружи. Итог A — наш минимум выполнен; F — сайт не открывать.

Дополнительно внешние сканеры (их отчёты сохранить в папку проекта с датой):

| Сканер | Приемлемо |
|---|---|
| SSL Labs (ssllabs.com/ssltest) | A или A+ |
| Mozilla HTTP Observatory | B+ или выше |
| securityheaders.com | A |

Это условие «готово» для шага 3.7. До появления сервера шаг не может быть закрыт.
